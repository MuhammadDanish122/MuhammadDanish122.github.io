Outcomes

What you will be able to do

Every row change reaches the warehouse, and you can prove it.

  • Configure MySQL binlog and Debezium so you capture every insert, update and delete, including during snapshots
  • Run a 3-node Kafka cluster in KRaft mode without ZooKeeper
  • Write Python consumers that commit offsets only after ClickHouse confirms the write (fail-closed)
  • Pick the right ClickHouse table engine for upserts and deletes from CDC
  • Reconcile source and warehouse down to the row id, and alert on drift
  • Backfill a table or a time window without double counting
  • Run a separate webhook consumer group off the same topics without slowing the warehouse

The examples use MySQL. The consumer, reconciliation and backfill chapters apply to any Debezium source, and the notes call out Postgres differences.

Is this for Kafka Connect sinks or custom consumers?

Custom Python consumers. Chapter 6 explains when the ClickHouse Kafka engine or a Connect sink is good enough and when it is not.

Which versions does it use?

Recent Debezium 2.x/3.x, Kafka 3.x/4.x in KRaft mode, and current ClickHouse. Version-specific settings are marked.
